# Bolts multiplayer protocol v3

One authoritative Rust process runs 60 Hz simulations and 20 Hz snapshots. Each lobby allows six participants, including spectators and temporary AI fill. Local AI matches never open a multiplayer connection. Lobby time is monotonic; rounds last 300 seconds and restart after eight seconds. Empty lobbies expire after five minutes; disconnected members have a 30-second reconnection grace.

HTTP endpoints (JSON):
- `GET /api/health` -> `{ok:true,version:3}`
- `POST /api/session` body `{token?:string}` -> `{playerId:string,token:string}`. Opaque browser-persisted bearer token; random UUID identity, token hash stored server-side. A supplied invalid token receives 401 (client may explicitly create a fresh session).
- `GET /api/lobbies` -> `{lobbies:[{id,name,players,bots,capacity:6,phase:"playing"|"ended"}],version:1}`. `players` counts human seats including reconnect reservations; `bots` is separate. Ensure an available lobby on demand. Do not create one on every polling request; join atomically allocates capacity.
- `GET /api/status` -> `{online:number}`. Connected human lobby participants, including spectators; excludes AI, unjoined sockets and disconnected reservations. No session required; 120 requests/minute/network.
- `POST /api/visits` body `{visitorId:string}` -> HTTP 204. UUIDv4 only, canonicalized to lowercase; unknown fields rejected and body limited to 256 bytes. Requires exactly one valid allowed Origin (including for non-browser clients); missing/disallowed Origin returns 403. Invalid UUID returns 400; malformed JSON/schema uses 400/422; oversized body returns 413; 60 attempts/minute/network returns 429; persistence failure returns 503 without stopping gameplay. Stores only visitor ID and server receipt times, deduplicated into UTC minute buckets. No session or player linkage and no public read endpoint. Frontend startup/visible-page heartbeats are optional and never awaited by gameplay.
- `GET /api/leaderboard` -> `{allTime:[{name,kills,deaths}],last24Hours:[{name,kills,deaths}]}`. All named human rows, including zero scores, sorted by kills descending, deaths ascending and canonical name. Plain names group case, whitespace and `^0`–`^9` color variants. Combat-time names retain historical credit; `Unknown Soldier` and bots are omitted. Human-vs-bot combat counts; self-kills count only as deaths. The second table uses a rolling 24-hour UTC window for both kills and deaths. No session required; 30 requests/minute/network.
- `POST /api/feedback` body `{message:string,email?:string}` -> HTTP 201 `{id:string}`. Message trimmed, required, 1–2000 Unicode characters; optional email trimmed and validated, at most 254 ASCII bytes. Blank email is omitted. Invalid fields return 400 `{type:"error",code:"invalid_message",message}`; malformed JSON/schema uses standard 400/422, body over 12 KiB returns 413. Rate limits are three attempts/minute and five accepted requests/hour/network; 429 uses `code:"rate_limited"`. The hourly limit survives restart. No session is needed and no public feedback-read endpoint exists.
- `GET /api/ws` WebSocket. Authenticate in first frame within 5 seconds. No token URL parameters.

All public community endpoints enforce the same exact browser-origin allowlist as session/lobby requests; disallowed origins receive 403. Feedback and email remain private in SQLite, with only a server-keyed network pseudonym retained for rate limiting. API responses never expose that metadata.

### GameLift directory extension

The managed directory keeps the combat WebSocket protocol at version 3 and extends discovery/admission:

- `GET /api/lobbies` -> `{version:2,locations:["ca","ny","sp","par"],lobbies:[{id,name,location,players,capacity:6,phase:"playing"|"starting",managed:true,pingUrl?}]}`. Every viewer receives the same global list. Only actual active/activating GameLift sessions appear; terminated sessions disappear, and `lobbies` can be empty. `locations` remains available for the location picker. Listing never allocates a game. `players` counts GameLift human/spectator reservations, including admission/reconnect grace, rather than AI actors.
- `POST /api/join` body `{token,lobbyId}` uses the permanent browser token only at the central directory. An actual lobby ID selects that game. `lobbyId:"new:ca"` (or `ny`, `sp`, `par`) reuses a reservation, fills an open game in that location, or places a new game if all are full or none exist. These routing keys are never lobby rows. Concurrent callers share one pending placement per location. HTTP 202 `{status:"starting"}` means poll with the same request after two seconds; HTTP 200 `{lobbyId,websocketUrl,ticket}` supplies a real session ID and temporary admission. An exact lobby that fills returns 409; location-based admission tries remaining capacity automatically. Other errors include invalid location (400), expired identity (401), rate limit (429), and temporary service/startup failure (503).
- Connect directly to `websocketUrl` and send the returned `ticket` in the initial `hello.token`, followed by the real `lobbyId` in `join`. Never send the permanent account token to a regional server. The ticket expires after five minutes and binds the global player UUID, game session and reserved player session. Reconnection obtains a fresh ticket from the directory.
- `pingUrl` is a direct regional WebSocket echo endpoint. Send `{type:"ping",nonce:string}` and receive `{type:"pong",nonce}`; up to three bounded echoes per connection, no identity or player-seat allocation. The browser displays its own median RTT, not a directory-supplied ping. An unavailable endpoint displays `—`.

Empty games close after five minutes and leave the directory on refresh; infrastructure scale-to-zero follows separately. The managed `/api/status` total includes GameLift reservations/grace. See [regional hosting and rollout](README.md#gamelift-regional-hosting) for capacity limits, locality and shutdown behavior.

With one or two connected humans, a lobby adds two authoritative AI actors as space allows. At three connected humans or zero humans it removes them. Human arrivals and reconnects have priority over AI; spectators count toward the threshold, disconnected seats do not. AI have regular physics/combat, delayed line-of-sight perception and imperfect aiming. Their persisted identities are marked as bots and cannot authenticate or appear in public leaderboards.

Client messages:
- `{type:"hello",version:3,token}` -> `{type:"welcome",version:3,playerId}`
- `{type:"join",lobbyId?:string,name,faction,spectator?:boolean}` -> `{type:"joined",lobbyId,lobbyName,actorId,cueSeq,snapshot}`. Missing lobbyId means quick join; choose open lobby, create if none. Missing spectator means combat participation. Existing membership reconnects to the same actor and retains its current mode. Explicit full lobby returns error.
- Binary MessagePack input: `[3,0,seq,tick,generation,forward,right,jump,walk,lean,yaw,pitch,ads,stanceCode,weaponCode,fire,reload,melee,shotTime]`. All 19 tuple elements are required; maximum 256 bytes, no trailing data, finite numbers and safe integer sequence/tick/generation. Stance codes are stand=0/crouch=1/prone=2; weapon codes are rifle=0/grenade=1. JSON input messages are rejected. `tick` is an absolute server tick and `generation` is the actor's `spawnGeneration`. Each command owns exactly one 1/60-second simulation interval. The server queues at most one command per tick, rejects late/duplicate ticks and ticks more than 30 ahead at arrival, and never advances simulation time in response to packet count. Missing ticks use neutral movement/actions/ADS/lean while gravity and timers continue. Actions execute only on their assigned tick. `Actor.ack` is the last command sequence actually applied; reconciliation discards commands through the **snapshot tick**, including missing intervals, and replays later ticks. New lives invalidate old-generation commands; reconnect clears the queue and resumes from the simulated ack. `shotTime` samples the remote display timeline, bounded to 200 ms lag compensation. Pause/chat sends neutral motion/actions/ADS. Network clients cannot submit unscheduled inputs; that API remains internal to server AI only.
- `{type:"chat",text}` (max256 Unicode chars, 3 per5seconds)
- `{type:"profile",name}` / `{type:"loadout",faction}` / `{type:"leave"}`
- `{type:"spectate"}` switches an existing participant to spectator without a death or score change. `{type:"loadout",faction}` returns a spectator to combat with a normal protected spawn, including when the faction is unchanged. Both share the loadout rate limit. Spectators have `spectator:true,alive:false`; input cannot move or attack, they have no collision/target body, and ordinary respawn timers do not apply. Camera movement and following stay local. Spectator mode survives reconnection and round restart.
- `{type:"ping",nonce}` -> `{type:"pong",nonce}` for the client's own heartbeat. Nonce is a finite number or a string of at most 64 UTF-8 bytes. These JSON values never set scoreboard latency. Control messages reject unknown fields and are decoded once before acquiring the game lock.

The server separately sends a WebSocket control Ping with a random 16-byte nonce every three seconds, with at most one outstanding probe. Browsers automatically echo control Pong. Only a matching, single-use reply on the current authenticated connection is timed by the server. Snapshot `Actor.ping` is integer RTT in milliseconds (capped at 999), or `null` before measurement, after ten seconds without a fresh result, and while disconnected. Connection replacement clears the old reading. Non-browser clients must implement the standard control Pong response; client-supplied timing is ignored.

Server messages:
- Binary MessagePack snapshot: `[3,1,lobbyId,eventSeq,tick,time,remaining,roundNumber,ended,winner,actors]`, bounded to 8192 bytes. Each actor uses [the shared 50-field order](../shared/actor-fields.json), with nested pose and input-timing tuples defined in [wire-schema.json](../shared/wire-schema.json). This is lossless full state, without rounding or a previous delta baseline. The initial `joined.snapshot` remains a named JSON object. [networkCodec.ts](../src/networkCodec.ts) decodes binary state into `{type:"snapshot",inputTiming:"tick-v2",lobbyId,eventSeq,tick,time,remaining,roundNumber,ended,winner,actors,events:[]}` before actor validation. The timing marker remains `tick-v2` because scheduled-input semantics have not changed. Each Actor is the complete camelCase frontend Actor minus ai, plus hipSpread, ack, `spawnGeneration`, `bot:boolean`, server-measured ping, and `inputTiming`. Stable numeric actor IDs per lobby; timestamps use -1000 instead of Infinity. Snapshots never expose persistent UUIDs.
- Actor `inputTiming` contains authority-derived per-stream counters `{received,late,missing,arrivalLead,shots,rewindClamped,shotAgeMs}`. `received` counts unique valid scheduled packets including late packets; `late` counts expired arrivals; `missing` counts unfilled active ticks after the first scheduled tick. `arrivalLead` is signed command tick minus authority tick at arrival. Life/disconnect resets clear these counters. `shots` includes accepted attacks, `shotAgeMs` is the latest requested rewind age, and `rewindClamped` counts requests older than the permitted 200 ms. None of these diagnostics grant authority to client timing claims.
- `{type:"events",lobbyId,roundNumber,tick,time,eventSeq,events}` is a separate ordered reliable batch, with at most 128 events. `eventSeq` increases across rounds in a lobby; `joined.snapshot.eventSeq` establishes the new connection's baseline. Each event carries its own round/tick/time, actor/victim generation, names and actor faction. Clients wait for a snapshot at least as recent as the batch, then deduplicate by sequence. Old-life effects cannot restart a killcam or alter a new life; kill-feed names remain available after roster departure. Kill and chat notifications publish only after database commit. A delayed committed kill can therefore appear in a newer envelope; use the event's own round/generation for effects.
- `{type:"cues",lobbyId,roundNumber,tick,time,cueSeq,events}` carries at most 128 shot/hurt/reload/bolt/switch effects, sent each simulation tick when present. `cueSeq` increases across rounds; `joined.cueSeq` establishes the connection baseline. Each cue has actor generation and, when applicable, victim generation and `hitGeneration` for the shot target. Hurt cues include authoritative `lethal` for prompt damage flash without advancing health or death state. Cues do not appear again in durable event batches. They can render before the corresponding snapshot without changing authority; the client deduplicates predicted effects, rejects older lives/rounds, and holds unknown future lives for at most 250 ms/128 events. Kill/spawn/end transitions retain the snapshot gate. Reload sound gets a bounded presentation lease until the matching snapshot or a cancellation cue. Live muzzle/contact effects start on receipt; authoritative shot timestamps remain unchanged for killcam.
- `{type:"chat",id,actorId,name,text,at}` from authenticated room members only, after persistence.
- `{type:"left"}` for explicit departure.
- `{type:"error",code,message}`. Codes include unauthenticated,invalid_message,lobby_full,lobby_missing,rate_limited,session_replaced,server_busy.

Client remaps self actor to local index 0 and keeps stable server IDs for collision tie-breaking. Prediction uses integer ticks and RTT-based scheduling with 2–8 ticks of adaptive slack learned from authority arrival feedback. RTT probes run every second. Lead increases are bounded and explicitly neutral; lead drains gradually after sustained healthy arrivals. Replay is bounded to 120 ticks. Input sends stop adding traffic above approximately 12 encoded commands of browser WebSocket backlog; one-shot actions are discarded during that interruption, never replayed as a burst.

Remote actors use an independent monotonic playback clock, a 100–180 ms jitter-aware target delay, and bounded 90–110% recovery speed. An exceptional backlog over one second resets playback; ordinary packet arrivals never force a timestamp jump. Collision prediction still samples authoritative history with at most 100 ms extrapolation. Camera-only correction uses a 45 ms decay with a 200 ms maximum tail and swept world clearance; movement and aim are not eased. Life transitions and corrections over 1 m reset the offset.

Each socket has an independent reader and writer, one replaceable unsent snapshot, and a bounded reliable queue. Immutable payloads reserve their publication order synchronously, then serialize lazily once in a writer outside the Hub/outbox locks; recipients share the encoded bytes. Snapshot publication happens only on the final catch-up step when due, with a wall-clock minimum interval of 41.7 ms (half-tick scheduling tolerance around nominal 20 Hz) to prevent cross-batch bursts. A snapshot waits for preceding reliable messages, preserving join/event ordering. Congested connections close instead of retaining unbounded events; state replacement cannot drop shot/kill events. SQLite runs on a dedicated bounded worker outside the Hub mutex. Gameplay writes have FIFO priority over queued optional HTTP work. The simulation accounts for elapsed wall time with at most eight catch-up steps per batch and 30 ticks of retained debt; severe overload is measured and discarded explicitly. Graceful shutdown stops ticks and admission, enqueues lifecycle records, drains accepted storage work and checkpoints outside the game lock.

Protocols 1 and 2 are rejected. Deploy the server, regional gateway (if enabled), and frontend as one coordinated protocol release. Browser credentials and database schemas are unchanged.

Only the server determines hits, damage, ammo, cooldowns, deaths, scores and respawns; local weapon presentation is provisional. Client killcam uses authoritative snapshot/shot history. Menus do not pause online simulation. Disconnect/reconnect and lobby expiration must release slots and persist events exactly once.
